# UI audit — Monopoly Madness Auction

7 October 2026. Reviewed `UI_PROMPT.md` against the current working copy, whose lobby displays **v1.1.7**. `arch.md` still labels its architecture v1.1.6. This is an audit report, not a redesign implementation.

**Highest priorities:** restore Roll Dice in workers mode; make phone action panels readable and reachable; fix negative-money signs; make dialogs/tiles keyboard accessible. A visual redesign should address these before auction effects or decorative polish.

## How this was checked

Read the prompt and current game components, then rendered the **existing components**, not invented redesigns, into 15 static offline HTML fixtures. Inspected all 15 at **390×844** and **1440×900** in the browser (30 layout observations); visually inspected the phone board/rent/auction/waiting room and desktop board. Fixtures use Global Edition properties and an eight-seat midgame (seven active, one bankrupt); waiting room uses seven of eight seats. They are synthetic states, not a played-through game.

`audit/ui-preview.cjs` transpiles the real TSX in memory and server-renders it with synthetic state. Only preview state initialization and backend imports are substituted; no application source is changed. Browser pages contain CSS/HTML, no JavaScript, and a restrictive content policy. Firebase is never initialized, and React effects never run. That permits safe geometry/readability review, but **does not verify live focus traps, button actions, animation smoothness, network lag, keyboard opening/closing, or an actual mid-range device**. Portal dialogs that only render after client mount were checked in source. Standalone trade/player/property/team/log fixtures show those components without the app's surrounding modal.

Preview files under `audit/ui-preview/` are **current-UI evidence**, not the prompt's requested polished redesign mockups. No redesigned HTML, production component changes, rules changes, dependency changes, commits, pushes, wiki writes or production Firebase actions were performed.

## Prompt assessment

The brief is useful: it describes actual variant mechanisms, keeps the existing stack, requires populated phone/desktop states, and asks for an implementation map rather than vague inspiration. **It should not be followed verbatim until these conflicts are resolved:**

1. **Mobile sheet versus board-only stage:** one action owner is the right state model, but forcing every action into the board centre produces U02. Amend presentation constraint to “one priority-selected action; board stage on desktop, accessible bottom sheet on phone.” This changes placement, not game rules.
2. **Do not change rule copy versus inaccurate rules:** existing RulesPanel still says creditor/bank asset transfer while neutral tiles are the chosen variant, promises automatic auctions when current Pass is optional, hardcodes GO minimum, and understates utility currency scale. Ask the designer to flag mismatches in a separate section, preserve copy in presentation work, and leave correction to a rules/documentation task. Do not beautify inaccurate copy as authoritative.
3. **No prop contract changes versus capabilities needed:** eligibility reasons, write outcomes, exact countdown duration/extension and draft progress may be unavailable to a leaf component. The “Data/props needed” section is essential; proposed additions must be separate from presentation changes, with backend impact explicitly identified.
4. **Draft UI and worker UI missing from enumerated mockups:** the broad component list includes draft and workers, but the eleven mockup screens include neither a distinct draft auction nor worker-assignment sheet. Add those and a build/mortgage property detail state, or require named variants within the related files.
5. **Static mockups cannot prove accessibility/performance:** semantic HTML/focus styles can be inspected, but demand a later interactive keyboard/reduced-motion audit and device performance check before declaring goals met.
6. **Fixed target sizes are examples, not acceptance coverage:** include 320/360px phone width, landscape, tablet, text zoom, long player names and multiple tokens on one tile. Use one responsive file per screen, not duplicated phone/desktop DOM presented simultaneously, unless comparison sheets are explicitly requested.
7. **Eight unique player identities:** current lobby offers six token options (`LobbySystem.tsx:36–43`) for up to eight players. Define duplicate-colour policy and add label/shape distinctions so the designer does not assume eight distinct selectable colours.
8. **Game-over requires real flow:** winner data exists; rematch/reset permissions do not automatically follow. Mockup must label unavailable rematch capability rather than suggest a functional action solely through layout.

## Presentation direction

The three biggest problems are hidden/unreachable actions, unreadable phone density, and ambiguous money/state signals. Retain the slate/cyan/emerald character but make the action stage mechanically clear: title, amount, remaining time and one primary action. The phone board becomes a spatial overview; the selected property's readable detail lives beside the current decision in a bottom sheet. Consistent signed currency, owner identity layers and explicit state labels reduce reliance on colour. Keep motion brief and causal, with a reduced-motion path. Auction drama should follow usability: stronger bid hierarchy and outbid status first, a countdown ring afterward. This direction preserves rule behavior and existing component responsibilities.

Suggested tokens (recommendation only, not applied): slate-950 canvas; slate-900 surface; slate-800 raised surface; slate-100 primary text; slate-300 secondary text; cyan-300 information; emerald-300 gains; rose-300 losses; amber-300 urgency. Use dark ink on bright filled actions. Type: 14px minimum main UI, 16px actions/body, 20px panel title, 28–36px principal money. Spacing: 4/8/12/16/24; radius 8/12/16; target 44px; motion 120/180/240ms opacity/transform, zero or near-zero in reduced mode. Board map labels need separate presentation rather than shrinking all information into 11 columns.

Small reusable pieces: `CurrencyAmount` (amount, signed, compact, exact accessible label); `PlayerIdentity` (player, compact); `TurnStatus` (actor, isMine, seconds); `ActionStage` (kind, title, children, footer); `PropertyStatus` (owner, mortgage/inactive/building/team signals); `AuctionStatus` (bidder, local name, amount, seconds). These are proposed, not added.

Data/props needed: per-action eligibility/reason for build/sell/mortgage; write pending/error/success result to retain forms; auction identity/start/end/extension for reliable ring; draft index/total (current queue is destructively shortened, so original total needs tracking if true “3 of 8” is required). Current timer, player/team identities, workers, mortgage/inactive flags and winner ids already exist. Do not reinterpret PropertyCard.isOwned as “owned by me.”
